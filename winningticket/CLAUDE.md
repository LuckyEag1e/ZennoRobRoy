# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this directory.

WinningTicket is a Python (discord.py) bot that runs a bracket prediction pool. It shares nothing with the other bot in this repo, so run every command from inside `winningticket/`.

## Commands

```
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt          # plus `pip install pytest pytest-xdist` for tests
python bot.py                            # needs DISCORD_BOT_TOKEN in .env
python cli.py                            # terminal REPL, no Discord needed (uses data/cli.db)
pytest -n auto                           # all tests, spread across CPU cores
pytest tests/test_scoring.py::test_scoring_wrong_pick_awards_zero   # single test
python -m sim                            # simulated tournaments through the real cogs (--help for options)
./deploy.sh                              # rsync to remote host + restart systemd service
```

Setting `DEV_GUILD_ID` in `.env` syncs slash commands to that one guild instantly. Without it, the bot syncs globally, which can take up to an hour. If commands show up duplicated after switching between the two, run `clear_global_commands.py`.

## Architecture

Logic is layered so most of it can be tested without Discord:

- `bracket.py`: pure logic with no discord.py or sqlite3 imports, on purpose. It generates the tree, derives slots, scores, and computes pick distributions on plain dataclasses. Unit tests target this module.
- `db.py`: the SQLite layer (`data/tourney.db`) with no discord.py imports. It converts rows to `bracket.Match`, owns the `STATUSES` list, and `load_bracket()` returns the `(matches_by_id, feeders_by_target, teams_by_id)` trio most commands need.
- `labels.py`: plain-text labels (teams, matchups, scores, pick shares) used by both the embeds and the CLI, so the two stay worded the same.
- `csv_import.py`: validates a round-1 CSV and creates the tournament and teams.
- `tournament_builder.py`: saves the match tree for round-1 pairs (used by both CSV import and closing registration). `seeding.py` is pure logic that puts entrants in seed order and turns that order into those pairs, giving byes to the top seeds.
- `ratings.py`: pure Elo logic, replaying past games into each user's singles and team ratings.
- `cogs/*.py`: slash commands and button/select views. `common.py` holds helpers shared across cogs (tournament lookup, autocomplete, `TournamentSession` for multi-step flows, match select menus). `embeds.py` and `ascii_bracket.py` handle rendering.
- `sim/`: simulated tournaments. `discord_fakes.py` stands in for Discord, `harness.py` dispatches commands, clicks, menu picks and forms the way discord.py and `bot.py` would, `checks.py` holds what's checked after every step, `harness.Crowd` interleaves actors (a scenario's `crowded`/`simultaneous`/`co_organizer` settings), and `actors.py`/`scenarios.py` hold the competence profiles, organizer styles and scenarios. When you add a command, give an actor a reason to use it (check `python -m sim --coverage`); when you add a format, add a scenario for it.
- `cli.py`: drives the same `db`/`bracket`/`labels`/`csv_import` code as the cogs. When you add or change a command, keep its CLI counterpart in step. `example_bracket.csv` is a small test bracket for it. Real tournament CSVs are gitignored because they contain people's names.

Concepts that span several files:

- **Only round 1 stores teams.** Later rounds' teams are derived each time through `resolve_slot`/`resolve_all_slots` by following `feeds_into_match_id`/`feeds_into_side` back to the feeder winners. The `winner_of` callback decides whose bracket gets resolved: point it at real `match_results` for reality, or at one user's predictions for their own bracket. `/predict` only offers round 2+ choices that come from the user's earlier picks.
- **Played rounds:** `Match.round` is the tree column, but everything players see, and scoring, uses `Match.played_round`, set by `bracket.assign_played_rounds` when `db` loads a bracket (a bye's is 0, since no game is played). It stays `None` until then, so hand-built test fixtures go through `tests/helpers.numbered`. The two only differ when two byes meet: that game sits in tree round 2 but is played in round 1.
- **Scoring** compares the predicted winner with the actual winner at the same `match_id`. A correct pick is worth `2 ** (played_round - 1)` points.
- **Byes** are round-1 matches with exactly one team. They advance automatically through `effective_winner`, never get a result row, and are hidden from `/predict`, `/match result`, and `/match stats`. Uneven brackets can also make a game's winner wait out a later round; `bracket.byes_in_round` finds both kinds for the bracket summary and `/mypicks`.
- **Registration:** `/registration open` creates a tournament at status `registration` with no matches. Sign-up commands reply privately, and the sign-ups announcement keeps a running count instead of the channel getting a post per sign-up. Entrants are stored in the `teams` table, a name kept from before sign-ups existed: each one is a single player for now, and team tournaments with several Discord users per entrant are planned. Each `/register` adds an entrant plus a `team_members` row linking it to the Discord user. Entrants with no members (from a CSV, or added by name with `/registration add`) have no Discord account behind them. Closing draws the entrants into a bracket through `tournament_builder.close_registration` and moves the tournament to `setup`, seeding them by rating or drawing them at random according to `tournaments.seeding_mode` (set by `/registration open`, overridable by `/registration close`, which saves the mode it used so `/history seeding` describes it correctly). It's done by hand, or by a loop in `cogs/registration.py` that checks every 5 seconds for a passed `registration_closes_at`. A close is all-or-nothing, so one that fails can simply be retried. `resolve_tournament` (`_require_tournament` in the CLI) turns away a tournament still in registration, since it has no bracket; commands that work without one pass `needs_bracket=False`. Closing first claims the tournament with a conditional status update (`db.claim_registration_close`), so a tournament can't be closed twice. Public announcements never name organizer commands, and the bot never DMs anyone: it should stay unobtrusive.
- **Tournament status** moves `registration` → `setup` (closing registration; CSV tournaments start at `setup`) → `predictions_open` (`/tournament open`) → `in_progress` (`/tournament lock`) → `completed` → `concluded` (`/tournament conclude`). `db.get_tournament_by_name` and the autocomplete skip concluded tournaments, so they keep their data but only `/history` (`cogs/history.py`, private replies) and `/admin linkplayer` reach them. Their names are never reused, so a name always means one tournament: a unique `(guild_id, name)` index enforces it, and `db.init_db` renames older databases' duplicates (from when names could be reused) by adding the date to all but the newest. Open and lock only move one step forward (`db.is_next_status`); `/admin setstatus` can force any status except `registration` and `concluded` (`db.FORCEABLE_STATUSES`): concluding can't be undone from Discord, and a tournament can only enter or leave registration by being opened or closed. Cogs gate their actions on the current status.
- **Consent:** an entry is only linked to a member's account (a `team_members` row) once they've agreed. At their first `/register` a private notice (`labels.CONSENT_NOTICE`, `ConsentView` in `cogs/registration.py`) offers Agree or Opt out. Agreeing is stored in `consents` and never asked again; opting out isn't stored, enters them by display name only (refused if that name is taken, since a name-only entry can't be told apart from another), and unlinks any entries from before consent was asked. A member who has agreed and signs up under the name of an entry with no account behind it takes that entry over (`db.register_entrant`) instead of getting a second, numbered one; `team_members.took_over` marks it, so `/unregister` gives the entry back instead of deleting it. `/optout` (typed confirmation; it works even for banned members) forgets the agreement and unlinks every entry in the server through `db.opt_out`. `/registration add user:` and `/admin linkplayer` only link members who've agreed, and `/admin linkplayer` won't link a second member to an entrant. `/admin unlinkplayer` (`db.unlink_entrant`, any status) unlinks one entrant and leaves the agreement alone; during sign-ups, a member who had taken that entry over (`took_over`) is also entered again under a numbered name, since otherwise their next `/register` would take it over again. A member's own entry is refused during sign-ups (`db.OwnEntryError`; `/registration remove` withdraws it instead), since left name-only it would count as taken over once they signed up again. Prediction picks aren't covered: they're always saved with the member's account, and the opt-out reply says so.
- **Ratings** are private: `/rating` shows members their own, and only organizers (Manage Server) can look up someone else. They're never stored. `db.load_match_history` collects every decided game from the server's concluded tournaments in the order they were played (oldest tournament first, then round by round; not by `recorded_at`, which changes when a result is corrected), and `ratings.compute_ratings` replays them (K=32, base 1500) whenever `/rating` or a seeded close needs them, so linking an old entrant to a member takes effect at once. A game counts only when both sides have Discord users behind them, and it's a team game if either side has more than one. Seeding sorts entrants by rating and writes `teams.seed`. The top seeds take any byes, and the rest are paired top half against bottom half: `standard` pairs best with worst (1v8), and `slide` pairs them in order (1v5) so the lowest seeds don't open against the best. Players with no rating count as 1500 (`seeding.place_new_entrants`), drawn at random among anyone else on exactly 1500. Besides `/history`, concluded tournaments are reachable only from `/admin linkplayer`, which links an old entrant (such as one from a CSV) to the member who played as them. Nothing can delete a concluded tournament or change its results, since `/history` shows them as they were.
- **Results** are only written through `db.record_result` and `db.clear_result`. They drop later results whose winner is no longer in that match (`bracket.stale_results`) and keep `completed` in step with whether the final is decided.
- **Admin permissions:** Discord ignores `default_permissions` on subcommands, so it's only set on the all-admin `/admin` group. Admin subcommands in groups members also use (`/tournament`, `/registration`, `/match`, `/help`) use `common.requires_manage_server`, a check at run time. Every command is guild-only.
- **Bans** are checked by `common.turn_away_if_banned`: `bot.WinningTicketTree` runs it before every slash command and autocomplete, and every button view and form runs it through its `BotView`/`BotModal` base class, so a ban also stops views already open. New views and forms must subclass those. The CLI checks in `onecmd`.
- **Feedback stays anonymous:** the `feedback` table has no user column and stores only the date. Keep it that way; the `/feedback` cooldown (`FeedbackCooldown`) is the only thing that knows who sent what, and it lives in memory.
- **Select menus** hold at most 25 options, so match choices go through `common.MatchPicker`, which pages.
- **Live posts:** `/tournament bracket` and `/tournament leaderboard` keep one post per tournament in the channel (`live_posts` table). A loop in `cogs/tournament.py` re-renders each every 5 seconds and edits it when it changed, so nothing that changes results, names or status has to refresh it. Asking again while the post is among the channel's last few messages gets a private link to it instead of a new post; otherwise a fresh post takes over and the old one is deleted, so the channel only ever holds the current one. Each `live_posts` row stores a fingerprint of what its post shows, so a restart doesn't re-edit (and mark "edited") a post that's already current; it's only saved while the row still points at that message, because a new post can replace the live one mid-refresh.
- **Menus go out of date:** a menu can sit open while someone else changes the bracket, so anything picked from one is checked against `db.match_now` (and `common.outdated_pick_message`) right before it's saved, with no `await` in between.

## Deployment

The bot runs as a systemd service on a remote host. The host, path, and user live in the gitignored `deploy.local.sh` (template: `deploy.local.sh.example`), and `DEPLOY_DIR` must be an absolute path because a `~` would expand on the local machine. `deploy.sh` never touches the remote `data/tourney.db` or `.env`. Only run one instance per bot token at a time, either locally or on the remote host. Two instances race over gateway events, and their databases drift apart without any warning.
